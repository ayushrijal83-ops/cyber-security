## The challenge

Level 16 hands you an **RSA private key** instead of a password. You log into
`bandit17` with that key over SSH — no password prompt at all.

I already had the key text. The problem was on my side: I'm on **Windows**, and
every time I ran `ssh -i sshkey17` it failed with:

```
Load key "sshkey17": invalid format
```

The key itself was fine. The **file** was wrong.

---

## Why Windows breaks SSH keys

Two things go wrong when you paste a key into a file on Windows:

| Problem | What happens |
|---|---|
| **CRLF line endings** | Windows editors end every line with `\r\n`. OpenSSH expects `\n` only. The extra `\r` becomes part of the base64 data → decode fails → "invalid format". |
| **UTF-8 BOM** | Notepad / PowerShell `>` often write 3 invisible bytes (`EF BB BF`) at the start of the file. OpenSSH reads them as part of the `-----BEGIN` line, doesn't recognise the header, and gives up. |

There's a third one that bites you *after* the format is fixed:

| Problem | What happens |
|---|---|
| **Loose file permissions** | Windows files inherit permissions from the parent folder, so other accounts can read them. OpenSSH refuses to use a private key anyone else can read: `UNPROTECTED PRIVATE KEY FILE!` |

## Step 1 — Write the key with Unix line endings

```bash
cat > /c/Users/ayush/sshkey17_fixed <<'KEY'
-----BEGIN OPENSSH PRIVATE KEY-----
...key body...
-----END OPENSSH PRIVATE KEY-----
KEY
```

**Breakdown:**

| Part | What it does |
|---|---|
| `cat` | Reads from standard input and prints it out |
| `>` | Redirects that output into a file (creates / overwrites it) |
| `<<'KEY'` | A **heredoc** — feeds every following line, up to the closing `KEY` marker, into `cat` as input |
| quotes around the marker | Quoting turns off variable and backtick expansion, so `$` and `` ` `` inside the key stay literal. **This matters** — an unquoted heredoc would mangle the key |

Why this fixes it: the heredoc is run by **bash**, which writes plain `\n`
newlines and no BOM. That's exactly the byte layout OpenSSH wants.

> The same file written by `Set-Content` or Notepad would have `\r\n` + BOM and
> fail again. The tool that writes the file is what matters, not the text.

---

## Step 2 — Verify before connecting

```bash
file /c/Users/ayush/sshkey17_fixed
ssh-keygen -y -f /c/Users/ayush/sshkey17_fixed
```

| Command | What it does |
|---|---|
| `file <path>` | Inspects the file's contents (not its extension) and reports the type. Output `OpenSSH private key` means the header parsed correctly |
| `ssh-keygen` | The OpenSSH key-management tool |
| `-y` | "Read a private key and print the matching **public** key" |
| `-f <file>` | Which key file to read |

`ssh-keygen -y` is the real test. It parses and decodes the key exactly the way
`ssh` does. If it prints an `ssh-rsa AAAA...` line, the key is valid — so any
later failure is a *network / auth* problem, not a format problem. That splits
the debugging in half before you touch the network.

---

## Step 3 — Lock down the file permissions

```bash
icacls 'C:\Users\ayush\sshkey17_fixed' /inheritance:r /grant:r "$USERNAME:F"
```

| Part | What it does |
|---|---|
| `icacls` | Windows tool for viewing / editing file ACLs (permissions). The Windows equivalent of `chmod` |
| `/inheritance:r` | **R**emoves inherited permissions — strips everything the file picked up from its parent folder |
| `/grant:r` | Replaces (rather than adds to) permissions for the user named next |
| `"$USERNAME:F"` | Give my account **F**ull control. Everyone else now has nothing |

On Linux the equivalent is `chmod 600 sshkey17_fixed` — owner read/write, nobody
else. Same idea, same reason: **a private key readable by others is a leaked
key**, so OpenSSH hard-refuses to use one.

## Step 4 — Connect and read the password

```bash
ssh -i /c/Users/ayush/sshkey17_fixed -p 2220 \
    -o StrictHostKeyChecking=no \
    bandit17@bandit.labs.overthewire.org 'cat /etc/bandit_pass/bandit17'
```

| Part | What it does |
|---|---|
| `ssh` | Open an encrypted shell session on a remote machine |
| `-i <file>` | **I**dentity file — authenticate with this private key instead of a password |
| `-p 2220` | Port. Bandit runs SSH on 2220, not the default 22 (lowercase `-p` for `ssh`, uppercase `-P` for `scp` — easy to mix up) |
| `-o StrictHostKeyChecking=no` | Skip the interactive "are you sure you want to continue connecting?" prompt on first connect |
| `bandit17@...` | user@host — log in **as bandit17** |
| `'cat ...'` at the end | A command to run remotely. SSH executes it, prints the output, and exits — no interactive shell needed |

That last part is the useful trick: **`ssh host 'command'` runs one command and
comes straight back.** No logging in, running `cat`, then `exit`.

---

## How key authentication actually works

No password is ever sent. The flow is:

1. The server has `bandit17`'s **public** key in `~/.ssh/authorized_keys`.
2. I connect and present my **private** key.
3. The server sends a random challenge; my client signs it with the private key.
4. The server verifies that signature against the stored public key.

The private key **never leaves my machine**. That's why guarding the file
(step 3) is the whole security model — anyone who copies that file becomes me.

---

## The lesson

When SSH says `invalid format`, the key is usually fine — **the file is broken**.
Check, in this order:

1. Line endings — must be `\n`, not `\r\n`
2. BOM — must not be there
3. `ssh-keygen -y -f key` — proves the key parses before you blame the network
4. Permissions — `chmod 600` on Linux, `icacls /inheritance:r` on Windows

| Command | Purpose |
|---|---|
| `cat > file <<'MARKER'` | Write a file with exact contents and Unix line endings |

| `icacls file /inheritance:r /grant:r user:F` | Lock a file to one user on Windows (`chmod 600` equivalent) |
